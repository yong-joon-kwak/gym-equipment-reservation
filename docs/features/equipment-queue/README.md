# 기능: 기구 사용과 대기열 (equipment-queue)

> 상태 값의 뜻은 [`docs/README.md` §2](../../README.md). `planned` = 범위와 최소 보장은 확정, 구현 전.
>
> 규칙의 값(노쇼 유예 2분·연장 5분 등)은 루트 [`README.md`](../../../README.md) §3 이 정본이다. 이 문서는 값을 되풀이하지 않고 **무엇이 깨지면 안 되는가** 만 정한다. 용어는 [`domain-glossary.md`](../../business/domain-glossary.md) 를 따른다.

## 왜 · 누가 · 어디까지

- **왜**: 이 시스템이 푸는 문제는 "지금 이 기구의 주인이 누구이고, 다음은 누구인가" 가 암묵적 합의에만 있다는 것이다(루트 README §1). 이 기능이 그 합의를 **사용 세션과 대기열**로 바꾼다.
- **누가**: 회원(`MEMBER`). 관리자는 기구를 쓰지 않으며 이 기능의 판정을 타지 않는다.
- **어디까지(범위)**: 태깅 판정(사용 시작 · 대기 등록 · 변화 없음 · 거부) · 만료 시각과 연장 · 본인 종료 · 대기 취소 · 차례 호출과 노쇼 · 지연 정리 · 현황과 기구 상세 조회. 그리고 그것을 쓰는 **현황 목록과 기구 상세 화면**.
- **범위 밖**: 기구 등록·비활성화·강제 종료(→ [`equipment-catalog`](../equipment-catalog/README.md)), 푸시 알림, 예약(미래 시각을 잡아 두는 것).

## 최소 보장 — 백엔드 (`apps/backend`, PHPUnit)

`#[Feature('equipment-queue')]` 라벨이 붙은 테스트가 보증한다. 한 줄이 깨지면 이 기능을 켠 채로 배포할 수 없다.

| # | 보장 | 티어 |
|---|---|---|
| Q1 | **한 회원은 동시에 한 기구만 쓴다.** 다른 기구를 태깅해 사용을 시작하면 이전 사용 세션은 전환 종료된다 | T1 · T2 · T3 |
| Q2 | **한 기구에는 진행 중인 사용 세션이 하나뿐이다.** 사용 중인 기구(차례 호출 중 포함)를 다른 회원이 태깅하면 대기 등록이 되고, 두 회원이 동시에 태깅해도 둘 다 시작되지 않는다 (DB 유니크 제약이 최종 보증) | T1 · T3 |
| Q3 | **만료 시각은 대기자가 있을 때만 생기고, 연장은 마감 임박 구간에서 한 번만 된다.** 대기자가 모두 빠지면 만료 시각도 없어진다 | T1 |
| Q4 | **차례는 대기 순서대로 넘어가고, 노쇼 유예 안에 오지 않으면 다음 대기자에게 넘어간다.** 호출 시각은 기록이 언제 남든 같고, 조회는 기록을 바꾸지 않으면서 같은 답을 낸다 | T1 · T2 |
| Q5 | **대기는 회원당 하나이고, 재대기 제한 중에는 같은 기구에 다시 대기할 수 없다.** 거부 사유는 각각 `already_waiting_elsewhere` · `requeue_blocked` | T1 |

> **한 줄을 여러 티어가 나눠 맡는다.** T1 은 "사실이 이렇다면 결정은 이것이다" 만 본다 — 다른 기구의 사용 세션 같은 사실은 테스트가 객체로 직접 만들어 넘긴다. 그 사실을 저장소에서 제대로 모으고 결정을 기록에 적용하는지는 T2, 동시 요청을 DB 가 막는지는 T3 가 본다. 그래서 한 줄은 **적힌 티어가 모두 초록일 때** 보장된다 — 2단계가 끝나도 Q1·Q2 는 절반만 초록이고, 4단계에서 완성된다.
>
> Q2 의 "차례 호출 중 포함" 이 호출된 회원의 자리를 지킨다 — 노쇼 유예 동안 기구는 사용 중으로 보이고, 다른 회원은 가로채지 못한다.
>
> 비활성 기구를 태깅할 수 없다는 보장은 기능 사이의 계약이라 [`equipment-catalog`](../equipment-catalog/README.md) 가 소유한다. 여기서 되풀이하지 않는다.

### 보장에서 뺀 것 — 왜 최소가 아닌가

| 규칙 | 빼는 이유 |
|---|---|
| 예상 대기 시간 | 근사치임을 화면에 밝히는 값이다. 틀려도 누구의 차례도 빼앗지 않는다 |
| 사용 중에 다시 태깅하면 변화 없음(종료 버튼 표시) | 어겨도 기록이 틀어지지 않고 화면 동작이 달라질 뿐이다. 프론트 보장에서 다룬다 |
| 대기 취소 · 본인 종료 | 한 줄짜리 상태 전이다. 깨지면 Q3(대기자가 빠지면 만료 시각이 없어진다)·Q4(종료되면 차례가 넘어간다)가 함께 깨진다 |

테스트가 이 규칙들을 다뤄도 된다. 다만 **보장 목록을 늘리지 않는다** — 목록이 명세를 옮겨 적기 시작하면 무엇이 최소인지 흐려진다([`test-as-specification.md`](../../coding/test-as-specification.md) §1).

## 최소 보장 — 프론트 (`apps/frontend`, Vitest)

- 서버가 거부하면 그 `reason`(`already_waiting_elsewhere` · `requeue_blocked` 등)을 그대로 노출한다 — 대기 가능 여부를 프론트가 다시 판단하지 않는다
- 연장 버튼은 기구 상세 응답의 **연장 가능 여부로만** 켜고 끈다 — 만료 시각을 보고 마감 임박을 스스로 계산하지 않는다
- 태깅 결과가 `unchanged` 이면 쓰는 중에는 종료 버튼을, 기다리는 중에는 순번을 보여 준다 — 새로고침이 종료나 재등록이 되지 않는다

> 판정의 소유자는 백엔드다. 프론트 보장은 "규칙이 옳은가" 가 아니라 "계약을 지켰는가" 를 본다([`api-contract.md`](../../architecture/api-contract.md) §7).
