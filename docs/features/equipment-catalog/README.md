# 기능: 운동기구 관리 (equipment-catalog)

> 상태 값의 뜻은 [`docs/README.md` §2](../../README.md). `planned` = 범위와 최소 보장은 확정, 구현 전.

## 왜 · 누가 · 어디까지

- **왜**: 사용·대기의 대상이 되는 기구 목록에 주인이 필요하다. 고장·철거된 기구가 태깅 가능한 채로 남으면 대기열의 보장이 의미를 잃는다.
- **누가**: 관리자. 로그인한 계정의 역할이 `admin` 이어야 한다.
- **어디까지(범위)**: 기구 등록 · 이름/종류 수정 · **1인 최대 사용시간 설정** · 비활성화(soft) · 목록 조회, 그리고 그것을 쓰는 **관리자 화면 하나**. 재고·정비 일정·사진 업로드는 범위 밖.
- **왜 이 기능이 따로 있나**: 기능이 하나뿐이면 `FeatureCoverageTest` 의 슬러그 실재성·커버리지 하한 검사가 사실상 동작하지 않는다. 그리고 **기능 사이의 계약**(비활성 기구는 태깅할 수 없다)이 생겨야 "판정의 소유자는 백엔드" 가 실제로 시험된다.

## 최소 보장 — 백엔드 (`apps/backend`, PHPUnit)

`#[Feature('equipment-catalog')]` 라벨이 붙은 테스트가 보증한다.

| 보장 | 티어 |
|---|---|
| 관리자가 아니면 등록·수정·비활성화가 거부된다 | T1 · T2 |
| 같은 식별 코드의 기구는 두 번 등록되지 않는다 (DB 유니크 제약이 최종 보증) | T3 |
| **비활성 기구는 태깅할 수 없다** — 거부 사유는 `equipment_inactive` | T1 · T2 |
| 비활성화하면 진행 중인 사용 세션은 강제 종료되고 그 기구의 대기는 모두 취소된다. 사용·대기 이력은 기록으로 남는다 | T2 · T3 |
| 일반 회원의 목록 조회에는 활성 기구만, 관리자 조회에는 비활성도 포함된다 | T2 |

> 세 번째·네 번째 줄이 `equipment-queue` 와의 계약이다. 판정은 **여기(백엔드)** 에서 하고, 대기열 기능(`equipment-queue`)도 프론트도 그 결과를 받기만 한다.

## 최소 보장 — 프론트 (`apps/frontend`, Vitest)

- 비활성 기구는 현황 목록에 나타나지 않는다
- 관리자가 아니면 등록·비활성화 조작을 렌더하지 않는다 (권한은 서버가 최종 판단)
- 서버가 `equipment_inactive` 로 거부하면 그 사유를 그대로 노출한다 — 프론트가 활성 여부를 다시 판단하지 않는다

> 첫 줄은 "거부를 미리 줄이는 편의" 이지 규칙의 출처가 아니다. 목록이 낡아 비활성 기구가 보이더라도, 최종 판정은 서버 응답으로 수렴시킨다([`api-contract.md`](../../architecture/api-contract.md)).
